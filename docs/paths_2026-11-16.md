# Execution paths and the Sankey view, 2026-11-16

The Kubit CEO's comment on the retrospective post asked for two
things: label every tool call with the fields it actually changed
and compare that to what the request asked for, and group runs by
execution path, because the runs that touch an extra field tend to
call the tools in a different order, and that thin branch is easy
to spot in a Sankey. This build does both.

## What it is

`agentopsworkbench/paths.py` reads the saved run records in
`runs/` and answers three questions per run:

- What path did it take? The ordered tool names from the trace.
  Policy, approval, and verify entries are not tools and do not
  count.
- What fields actually changed? A diff of store_before against
  store_after, per customer.
- What did it change that the request never asked for? Changed
  fields minus the fields in the request inputs. A change to a
  customer other than the target counts as extra by definition.

Runs are grouped by path, with outcome counts and a count of runs
that changed an extra field. The Sankey diagram shows the flows:
start -> first tool -> ... -> outcome, with widths by run count
and outcomes colored (green succeeded, amber refused/denied, red
failed/verification_failed).

## How it renders

The SVG is built by hand in `render_sankey_svg`, no new
dependency. Plotly was not installed and adding it would have
meant another install step on the Mac; the diagram is small
enough that a pure layout (columns by depth, nodes stacked by
flow, bezier ribbons) does the job. Nodes are (depth, label)
pairs, so the same tool at a different depth is a different
node, which keeps the diagram correct for any path shape.

## UI

A fifth tab, Paths, shows the Sankey plus a table: path, run
count, outcomes, and runs with extra field changes. A Refresh
button recomputes from `runs/`.

## Verification (2026-11-16, sandbox)

- Tests: 71/71 (12 new). The key ones: the path ignores
  non-tool trace entries, the extra-field check flags both a
  silent change to the target record and a change to another
  customer, and the Sankey flow from start sums to the run count.
- v1 golden: 10/10, zero unauthorized mutations.
- Adversarial set: 4/4, eval gate SHIP, zero mutations.
- Real runs: 5 saved runs group into 3 paths (2 succeeded on the
  full read-then-write path, 2 succeeded on a read-only path, 1
  refused with no tool calls), 0 with extra field changes.
- UI: answers HTTP 200, all five tabs present, the Sankey SVG
  and the path table present in the served config. The SVG
  geometry was checked numerically: all coordinates inside the
  canvas, no negative values.

## Label fix, later the same day

On her Mac the diagram showed `update_customer_email (6)` and
`succeeded (6)` jammed together. The cause was the layout: the
last column's label was drawn to the left of its bar, straight
into the previous column's label. The fix draws every label to
the right of its bar and widens the SVG to fit the last column's
label (930 wide for a three-deep diagram). A regression test
renders a 6-succeeded-plus-1-denied set and asserts no two
labels on the same row overlap. Tests 72/72 after the fix.
